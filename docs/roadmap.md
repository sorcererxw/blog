# Blog2 Roadmap

## Mission

Maintain the standalone public blog application in `/Users/sorcererxw/repo/sorcererxw/blog`, deployed on Cloudflare, while preserving the public blog experience and required async workflows.

## Architecture Proposal Under Review

- `docs/specs/2026-04-14-blog2-astro-migration-design.md` proposes replacing the Next.js/OpenNext runtime with Astro + the official Cloudflare adapter
- this direction was approved on 2026-04-14
- implementation starts with secret rotation, measurable success criteria, and route-parity proof before framework cutover
- Astro platform rebase is now in progress: package scripts, route entrypoints, Cloudflare adapter wiring, preview-time URL parity for the core public routes, retirement of the old `src/app/**` runtime entry files, and stable builds after moving article detail to on-demand rendering are in place
- repository extraction from `tempura/web/apps/blog2` to standalone `/Users/sorcererxw/repo/sorcererxw/blog` happened on 2026-05-04 with `blog2` history preserved

## Current Product Boundaries

Included:

- public blog pages
- article listing and article detail
- projects
- stack
- thoughts / Telegram-derived public content
- sitemap and metadata
- content normalization from Notion
- translation and related async workflows
- image metadata support for rendered content

Excluded:

- `fusink`
- route management/admin tooling
- generic OAuth/admin flows from the old backend
- non-blog backend products

## Source of Truth and Storage

- Source of truth for content: Notion
- App-owned derived storage: Cloudflare KV
- approved exception: thoughts public content is now a checked-in snapshot generated by a local sync command
- Future escape hatch: optional partial migration to D1 if KV-only storage becomes too awkward for async workflows

## Milestones

### M0: Documentation and Operating Harness

Status: Done

Goals:

- establish the design spec
- establish `AGENTS.md`
- establish roadmap, task ledger, and verification docs
- create a working execution harness for future agents

Exit criteria:

- the operating docs exist at the standalone repo root and under `docs/`
- future work can be executed without rereading the entire repository

### M1: App Foundation

Status: In progress, sufficient to start M2

Goals:

- preserve the current `blog2` public behavior while the framework baseline moves from Next.js/OpenNext to Astro + the official Cloudflare adapter
- keep the shared domain/integration code reusable during the route-layer cutover
- configure the Astro/Cloudflare deployment baseline
- establish the target env and binding model
- preserve base layout, shell, logging, and boundary behavior during the migration

Exit criteria:

- the app builds
- the app can run locally
- the app can be deployed to Cloudflare in a minimal Astro-backed state
- remaining developer-experience polish can be deferred if it does not block public-read migration

### M2: Public Read Path

Status: Not started

Goals:

- implement article listing
- implement article detail rendering
- implement projects
- implement stack
- implement sitemap
- implement Notion fetch + normalization + KV-backed caching

Exit criteria:

- main public pages render from `blog2`
- public read traffic no longer requires the old public blog backend for these slices

### M3: Secondary Public Features

Status: In progress, with the narrow search-native SEO wedge implemented locally and pending submit/deploy verification

Goals:

- implement thoughts / Telegram-driven public pages
- introduce Cloudflare-backed image delivery for public media surfaces
- add image metadata support
- restore required SEO, comments, and route compatibility details
- land the approved search-native SEO slice with one narrow engineer-facing query wedge before any broader content-taxonomy expansion

Exit criteria:

- public behavior approaches feature parity with the current blog

### M4: Async Workflow Migration

Status: Not started

Goals:

- migrate translation jobs
- migrate retranslate capability
- migrate Telegram refresh jobs
- migrate content refresh and invalidation flows

Exit criteria:

- the old Go blog backend is no longer required for the public blog domain

## Sequencing Rules

- prefer vertical slices that can be deployed and verified independently
- avoid broad platform work before a public feature requires it
- keep the first version simple, especially around storage and infra
- document migration findings as they are discovered

## Known Architectural Constraints

- greenfield app, not an in-place refactor of `web/apps/blog`
- Notion remains authoritative for content
- KV remains the default storage choice unless docs are updated
- legacy code is reference material, not target architecture
- the active framework migration target is Astro, not continued expansion of the old Next.js route layer

## Active Priorities

1. complete `M1` Slice 0 for the Astro migration: baseline metrics, parity checklist, and explicit freshness decisions
2. stop broad framework churn outside the approved Astro migration plan
3. preserve article listing and article detail behavior as the first public-read parity targets during route cutover
4. keep thoughts on the current snapshot flow during the framework migration
5. treat the approved SEO work as a narrow M3 content/discovery slice, not as broad new product scope
6. keep the first SEO wedge focused on existing proof pages plus one manually authored query-entry page

## Open Questions

- which Cloudflare deployment mode should be the default baseline for this app
- what minimal Notion-to-app domain model should be established before migrating the first public article slice
- which public slice should land first: article listing or article detail
