## Summary

Migrate `web/apps/blog2` from Next.js to Astro in place, while keeping the product surface and the domain/integration logic intact.

This is a route-layer, rendering-layer, and deployment-layer replacement. It is not a content-model rewrite.

## Success Looks Like

- Astro owns routing, layouts, metadata, and Cloudflare deployment
- existing public pages render with no visible regressions
- only truly interactive UI hydrates on the client
- domain logic and Notion normalization stay in plain TypeScript modules
- OpenNext and Next-specific config disappear
- the migration has a measurable operational or user-facing win, not just cleaner taste

## Premises

1. `blog2` is content-first enough that Astro is a better long-term fit than Next.js.
2. We should optimize for a simpler final architecture, not minimum short-term code churn.
3. The migration should happen in `web/apps/blog2`, not in a parallel replacement app.
4. We should preserve public behavior before adding new features.
5. We should treat committed secrets in `src/config/server.ts` as a migration blocker for any real cutover.

## Current-State Constraints

- current framework entrypoints live in `src/app/**`
- `src/app/layout.tsx` depends on `next/font/google`
- shared navigation and some views depend on `next/link` / `next/navigation`
- deploy chain depends on OpenNext (`open-next.config.ts`, Next dev/build/preview scripts)
- there are committed secrets in `src/config/server.ts`
- `projects` and `stack` currently have `revalidate = 600`, so their freshness behavior needs an explicit Astro replacement
- `/stack` is currently hidden from production navigation via `getRuntimeConfig().isProduction`, so "same public surface" is not fully specified yet
- custom `not-found` and route error states live in framework files today, not in domain modules

## Measured Success Criteria

We should not approve a framework rewrite without explicit proof targets.

Baseline before implementation:

- current local dev loop pain points and workaround count
- current preview/deploy chain steps
- current build/preview time

- any concrete SEO or performance deficits we can measure

Approval threshold:

- the Astro path must materially simplify the deploy/runtime chain or improve page-delivery behavior
- and it must do so without increasing product regressions or pushing async migration farther out

## Migration Preconditions

## Freshness Decision

`/projects` and `/stack` will preserve the current `10 minute` freshness target during the Astro migration.

That means the first Astro implementation for these routes must not silently degrade to "only refresh on deploy."

Acceptable implementation directions:

- on-demand rendering with explicit cache headers
- a platform-owned cache layer that preserves the current freshness contract

Rejected direction:

- build-time-only output for `/projects` or `/stack` in the first migration slice

## Failure Modes Registry

| Failure mode | Severity | Why it matters | Mitigation |
| --- | --- | --- | --- |
| Route parity breaks during file move | high | user-visible 404s or broken links | migrate routes with HTTP route checklist and browser sweep |
| Mixed Astro/React boundary causes hydration bugs | medium | interactive stack filter stops working or over-hydrates | isolate the island to one component and test only that surface |
| Cloudflare adapter/runtime mismatch | high | local success, production failure | verify with `astro preview` and Wrangler-backed preview, not dev-only confidence |
| Secret rotation is skipped | critical | production credential exposure continues | make secret externalization a required cutover task |
| Projects/stack freshness semantics accidentally regress | medium | stale content without anyone noticing | make freshness choice explicit and verify with docs + headers |

## Error and Rescue Registry

| Problem | Rescue path |
| --- | --- |
| Astro route migration stalls on framework-specific components | keep the component in React, remove only the Next import, and render it from `.astro` |
| Cloudflare preview differs from local dev | treat `astro preview` as the release gate, not `astro dev` alone |
| `workerd` rejects a dependency | precompile or isolate that dependency; if it is only used in local scripts, keep it out of runtime code |
| Regressions pile up across too many routes at once | cut the migration in the slice order above and land one vertical route family at a time |

## Design Review

The design risk is not "Astro pages will look different." It is that several user-visible behaviors are currently encoded in framework files and shell logic, while the migration docs describe only route moves.

Critical parity gaps that must be explicit:

- `/stack` is hidden from production nav today, so the public surface is not actually fixed yet
- home metadata is generated from Notion today
- the custom `404` and route error boundary are part of the user experience
- article, project, stack, and thoughts empty states all carry product copy that can regress during rewrites

### Design Decision

Add the user-visible parity checklist and require it before route migration.

## Engineering Review

The main implementation ambiguity is freshness and runtime ownership.

`/projects` and `/stack` currently combine `force-static` with `revalidate = 600`, so the Astro replacement cannot just say "static by default" and hope for the best. The migration needs an explicit decision on whether those routes stay runtime-backed, become build-time-only, or move behind a content-sync trigger.

The second ambiguity is platform injection. Astro/Cloudflare env access should stay in framework-owned adapters and not spread into domain modules.

### Engineering Decision

Do not start Slice 3 until:

- the `/projects` and `/stack` freshness policy is documented
- the Cloudflare binding adapter shape is written down

## DX Review

This is not a developer product, but the migration materially changes the maintainer loop.

The new stack only improves life if contributors still have a one-command local entrypoint, a trustworthy preview that matches Workers runtime behavior, and actionable env/setup failures.

### DX Decision

- `pnpm --dir web --filter blog2 dev`

- fix the current `dev -- --hostname ...` argument-forwarding bug as part of the maintainer-loop cleanup
